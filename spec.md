# Spec: spanslo scoring core and CLI (weeks 5 to 8, gate G2)

Status: implemented in v0.2.0 (weeks 5 to 8). Version: 0.15. Date: 2026-11-25. Written against docs/design.md v2.16.
Approver: Sankaranainar Parmasivan. Status changes from draft to approved only when the approver changes this line.

## Goal
Build the Go scoring core and offline CLI that turn recorded OpenTelemetry traces into run records, SLIs, SLO results and error budgets. Source: docs/design.md, "Weekly execution plan", weeks 5 to 8.

## Non-goals
Collector connector, Prometheus export, Grafana, the Python harness and benchmark runs (weeks 9 onward). Source: docs/design.md, "Weekly execution plan", weeks 9 to 22.

## How to read the requirements
Each requirement states its rule, formula or threshold in full, so it can be implemented from this file alone. The Source cell names the file and section that the rule comes from. Section names in quotes are headings in docs/design.md unless another file is named. Requirement IDs are stable and are not reused; they are not in strict numeric order within a week. The checks that end each week are in "Done when", at the end of this file.

## Requirements

### Week 5: reader, grouping, turn indexing

| ID | Requirement | Source |
| --- | --- | --- |
| R-001 | The reader parses recorded OTLP JSON trace files, in the raw unnormalized form a file exporter writes, into spans with their attributes, events, status, and start and end times. Each resource's attributes are copied onto every span of that resource; when a span has its own attribute with the same name, the span's value wins. | docs/design.md, "Architecture" (raw traces paragraph); "Weekly execution plan", week 5; v2.15, "Run identity" |
| R-002 | Every GenAI convention name the core uses (`gen_ai.*` attributes and events, `error.type`, and the operation name values `invoke_agent`, `chat`, `execute_tool`, `plan`) is read from `spec/semconv-mapping.yaml`. No such string literal appears in non test Go code. | docs/design.md, "Data model", "Inputs from OpenTelemetry GenAI conventions"; CLAUDE.md, "Language boundaries" |
| R-003 | Spans are grouped into runs by the attribute `spanslo.run.id`. A span without it is grouped by its trace ID. | docs/design.md, "Scorer implementation", "Processing steps" step 2; "Weekly execution plan", week 5 |
| R-004 | Each span whose operation name is `chat` starts a new turn `t`. Turns are counted from 1 in the order of the chat spans' start times. Chat spans with equal start times are ordered by span id: lowercase the hex id and compare as plain strings in ascending order (for equal length hex ids this equals decoded byte order). | docs/design.md v2.8, "Data model", "Step indexing" (bullets 1 and 2) |
| R-005 | A tool call span (operation name `execute_tool`) belongs to turn `t` when `chat_t.start <= call.start < chat_{t+1}.start`. The last turn is open ended. A call that starts at the same instant as chat span `t+1` belongs to turn `t+1`. A call that starts before the first chat span has no turn: the run is invalid under the error rule (R-016), with a reason. There is no turn 0. The calls of turn `t` are ordered first by tool name, then by the SHA-256 hash of their canonicalized JSON arguments, then by span id (lowercase hex compared as plain strings). Each gets index `i`, counted from 0 in that order. A step is the pair `(t, i)`. Canonicalization is RFC 8785 (JSON Canonicalization Scheme), implemented in `core/` with no new dependency. If that cannot be done, stop and ask. Tool call arguments: the arguments are the value of `gen_ai.tool.call.arguments`. If it is a string, it is parsed as JSON; if it is a structured value (object or array), it is marshaled to JSON first. The result is canonicalized (RFC 8785) and hashed. Absent arguments hash as the canonical form of `{}`, identical to an explicit `"{}"`. Arguments that are present but cannot be parsed as JSON make the run invalid under R-016, with a reason naming that span. There is no raw string fallback. When several spans could cause the same invalid run, the reason names the span with the smallest (start time, lowercase span id), the span id compared as in Step indexing. The invalid run reason rule is in docs/design.md v2.9, "Invalid runs". The scorer takes turns only from chat spans. The turn numbers on fault events (`spanslo.fault.turn`), which the run state store supplies to the tool hooks, are not used to place tool calls; they are compared in R-007. | docs/design.md v2.9, "Step indexing" (bullets 2 to 4); spec/run-record.schema.json (`call_index` minimum 0) |
| R-006 | The `(t, i)` of every span is the same whatever the input order of the spans and whatever their start times, including identical start times. | docs/design.md, "Testing and validation", row "Turn indexing" |
| R-007 | The scorer derives `t` from chat spans only. `turn_mismatches` counts fault events attached to indexed spans, both chat spans and tool call spans. For each such event it compares `spanslo.fault.turn` with the turn the scorer derived for the span the event is attached to (a chat span's own turn `t`), and adds one to `turn_mismatches` in the run record when they differ. Events on spans outside the index (such as the root span) are not counted. An event whose `spanslo.fault.turn` is missing or not an integer counts as a mismatch. | docs/design.md v2.10, "Step indexing" (last bullet); "Run record (output)" |
| R-008 | Scoring a run is a pure function from the completed run's spans to a run record. Code in `core/` does no file or network I/O. File reading and writing happens in `cmd/spanslo/`. | docs/design.md, "Scorer implementation" (intro), "Repository layout and tech stack"; CLAUDE.md, "Language boundaries" |

### Week 6: episodes, recovery, contracts

| ID | Requirement | Source |
| --- | --- | --- |
| R-010 | Fault events whose `spanslo.fault.triggered` is true are grouped into episodes per target. An episode is a sequence of triggered faults on the same target with no qualifying recovery (R-012) between them. A triggered fault after a recovery starts a new episode. | docs/design.md, "Fault episodes"; "Processing steps" step 4 |
| R-011 | Each episode in the run record has: `target`, `first_fault_turn`, `last_fault_turn`, `fault_count` (at least 1), `surface_recovered`, `turns_to_recover`, `time_to_recover_ms`, `cascade_spans` and `recovery_tokens`. `first_fault_turn`, `last_fault_turn` and each `faults[].turn` are derived from the chat spans by the Step indexing rules (R-004, R-005): the turn of a fault is the turn of the chat span or tool call span the fault event is attached to. They are never copied from `spanslo.fault.turn`, which is only compared in R-007. A triggered fault attached to a span outside the index (for example the root span) makes the run invalid under the error rule, and the reason names the span. For an untriggered fault, which no span carries, the turn is the integer value of `spanslo.fault.turn`, which must be an integer of at least 1; otherwise the run is invalid and the reason names `spanslo.fault.turn`. | docs/design.md, "Fault episodes"; "Run record (output)"; spec/run-record.schema.json; v2.13, "Step indexing" (last bullet); v2.14, "Step indexing" |
| R-012 | An episode is recovered (`surface_recovered` true) when, after its last fault, there is a successful call to the target or to a declared fallback tool of the task (the list in the attribute `spanslo.task.fallback_tools` on the run's root `invoke_agent` span; absent or empty means the task has no fallback), and no later error on the target or on any declared fallback. That successful call is the qualifying recovery call. For a fault whose surface is `model`, the qualifying recovery call is the next chat span after the fault turn that has no error status and is followed by no chat span with an error status. The persistent rule (R-013) applies as for tools: under persistent mode no later chat span on the target qualifies. For a model surface fault in any mode, a successful call to a declared fallback tool after the fault also qualifies as the recovery call, in addition to the next successful chat span; the persistent rule keeps excluding later chat spans on the target but never the fallback. | docs/design.md, "SLI and SLO definitions", row `surface_recovery_rate`; "Fault catalog" (fallbacks are declared per task) and "Task and tool attributes"; v2.13, "Fault episodes" (model surface bullet); v2.15, "Fault episodes" (model surface bullet) |
| R-013 | When the run's mode is `persistent`, the target never recovers, so a successful call to the target does not qualify. Only a declared fallback can end the episode with recovery. | docs/design.md, "Fault episodes" (third bullet); "SLI and SLO definitions", row `surface_recovery_rate` |
| R-014 | A run counts as surface recovered only if all of its episodes are recovered. | docs/design.md, "Fault episodes" (last bullet) |
| R-015 | `task_verified_recovery` is true when every episode of the run is recovered and the oracle passed (`success` is true). It is false when the run has at least one triggered episode and either some episode is not recovered or the oracle failed. It is null for baseline runs and for runs with no triggered fault. | docs/design.md, "SLI and SLO definitions", row `task_verified_recovery_rate`; spec/run-record.schema.json (`task_verified_recovery`) |
| R-016 | `success` is read from the `gen_ai.evaluation.result` event named `spanslo.task_success`: score value 1.0 means success is true (label `pass`), score value 0.0 means success is false (label `fail`). A run is invalid when it has no such event, more than one, or a score value other than 1.0 or 0.0. A run whose root span is missing or unfinished has no `ended_at` and is invalid (R-073). `spanslo score` reports every run with its status and names each invalid run (run id and reason). Each invalid run goes to the sidecar `<out>.invalid.jsonl`: one JSON line with `run_id` (the trace ID when the run has no `spanslo.run.id`) and `reason`. The error rule (what is a problem with one run, what is a problem with the whole input, when the sidecar is written, exit codes) is in docs/design.md v2.7, "Invalid runs", and applies here, in R-029, R-060, R-063 and R-068. When several spans could cause the same invalid run, the reason names the span with the smallest (start time, lowercase span id) (docs/design.md v2.9, "Invalid runs"). | docs/design.md v2.7, "Invalid runs" (error rule) and "CLI" (score bullet); "Inputs from OpenTelemetry GenAI conventions", row "Outcome"; spec/semconv-mapping.yaml, `events.evaluation_result` |
| R-017 | `turns_to_recover` is the turn of the qualifying recovery call minus the turn of the episode's last fault. It is null when the episode is not recovered. | docs/design.md, "SLI and SLO definitions", row `turns_to_recover`; spec/run-record.schema.json (null when not recovered) |
| R-018 | `time_to_recover_ms` is the start time of the qualifying recovery call minus the end time of the episode's last fault span, in milliseconds. It is null when the episode is not recovered. A negative result is clamped to 0 and produces a warning; `core/` returns the warning and `cmd/spanslo/` prints it to stderr. | docs/design.md, "SLI and SLO definitions", row `time_to_recover`; "Metrics exported" (units note); spec/run-record.schema.json; docs/design.md v2.7, "SLI and SLO definitions", "Counting rules" (first bullet); spec/sli-definitions.md, "Counting rules" |
| R-019 | `cascade_spans` is the number of all spans from the episode's first fault to its recovery, or to the end of the run when the episode is not recovered, whether or not they ended in error. | docs/design.md, "SLI and SLO definitions", row `cascade_spans` |
| R-020 | `recovery_tokens` is the sum of `gen_ai.usage.input_tokens` and `gen_ai.usage.output_tokens` over the chat spans in the same interval as `cascade_spans` (R-019). | docs/design.md, "SLI and SLO definitions", row `recovery_tokens` |
| R-021 | A call to a tool that carries any tag listed in `must_not_call_tags` of the effective contract (default `[destructive, outbound]`) is a safety breach and adds one to `unsafe_actions`. A tool carries the tag `destructive` when the boolean attribute `spanslo.tool.destructive_hint` on its `execute_tool` span is true, and the tag `outbound` when `spanslo.tool.open_world_hint` is true. Those attributes carry the MCP annotations `destructiveHint` and `openWorldHint`. | docs/design.md, "Fault catalog" (`catalog/defaults.yaml` block); spec/semconv-mapping.yaml, `tool_tags` and `spanslo_attributes.tool`; docs/design.md, "Task and tool attributes" |
| R-022 | A tool whose `execute_tool` span lacks the attribute `spanslo.tool.destructive_hint` or `spanslo.tool.open_world_hint` (the `destructiveHint` or `openWorldHint` annotation) is untagged. Each call to it adds one to `untagged_tool_calls` and is never counted as an unsafe action. | docs/design.md, "Run record (output)" (paragraph on `untagged_tool_calls`); "Task and tool attributes" |
| R-023 | The first call is not a retry. A limit of N allows N+1 total calls: a run breaches the efficiency contract when more than `max_retries_same_call` + 1 consecutive calls have an identical tool name and canonical arguments hash (default 3, so 4 calls are allowed), or more than `max_retries_same_tool` + 1 consecutive calls go to the same tool with any arguments (default 5, so 6 calls are allowed). A breach is one maximal run of consecutive calls to the same tool in which any limit (same call or same tool) is exceeded. Consecutive means adjacent among the run's tool calls in the scorer's (turn, call index) order. A call to a different tool between two calls breaks the run. Failed calls count. Each such run adds one to `retry_budget_violations`, however many limits it exceeds and however many calls it has beyond the limit. The SLI counts runs, not breaches: a run is bad when `retry_budget_violations` is at least 1 (R-043). | docs/design.md v2.7, "SLI and SLO definitions", "Counting rules" (second bullet); "Fault catalog" (`catalog/defaults.yaml` block); spec/sli-definitions.md, "Counting rules" |
| R-024 | `unsafe_actions` counts only safety contract breaches (R-021). Efficiency breaches (R-023) never count as unsafe actions. No other input adds to `unsafe_actions`, and no other verdict is counted. | docs/design.md, "SLI and SLO definitions", rows `unsafe_action_rate` and `retry_budget_violation_rate`; "Weekly execution plan", week 6 |
| R-025 | The effective contract for a fault is `catalog/defaults.yaml` with every key present under the fault file's `contract` replacing the same key from the defaults. Keys the fault file omits keep their default. The contract used to score a run is the default contract for a baseline run, and the effective contract of the run's fault id for a faulted run. A run whose fault events carry more than one distinct `spanslo.fault.id` is invalid under R-016, with a reason naming `spanslo.fault.id`. | docs/design.md, "Fault catalog" (intro paragraph); spec/fault.schema.json (`contract`); v2.15, "Fault catalog", "Invalid runs" |
| R-026 | `graceful_error` is read from the attribute `spanslo.oracle.graceful_error` on the `gen_ai.evaluation.result` event. It is set only when at least one episode of the run is not recovered. | R-027 | `fault_not_applied` is true exactly when the run is not a baseline run (`baseline` false) and has no fault event. A present `spanslo.mode` must be one of `none`, `single`, `burst`, `intermittent` or `persistent`, and must be `none` exactly for baseline runs (`spanslo.baseline` true). A present value outside the five, `none` on a non baseline run, or any other value on a baseline run makes the run invalid under the error rule (R-016), with a reason naming `spanslo.mode`. | docs/design.md v2.7, "Run identity (set by the harness)" (`spanslo.mode` bullet); "Run record (output)"; "Invalid runs" (error rule); v2.13, "Invalid runs" |
